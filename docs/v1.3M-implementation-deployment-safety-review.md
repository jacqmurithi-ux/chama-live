### v1.3M.2.2 — Migration Safety Revision

Three blockers were addressed in Git only.

#### 1. Complete final authoritative validation

The allocation guard now re-reads and validates **every affected OLD/NEW payment target** and **every affected OLD/NEW obligation target** after the deterministic row-lock loops.

- UPDATE targets are de-duplicated.
- Validation is deterministic by UUID.
- No second accounting lock is acquired.
- Final NEW payment/obligation lineage is still checked separately.
- The implementation no longer relies on the last `v_payment_id` or only `NEW.obligation_id`.

#### 2. Exact rollback fidelity

The exact pre-migration trigger definitions were re-inspected read-only before the rollback artifact was created.

Pre-migration definitions restored by the rollback artifact:

```sql
CREATE TRIGGER prevent_closed_month_contribution_trigger
BEFORE INSERT OR DELETE OR UPDATE
ON public.contributions
FOR EACH ROW
EXECUTE FUNCTION public.prevent_closed_month_contribution();

CREATE TRIGGER trg_validate_monthly_payment_domain
BEFORE INSERT OR UPDATE OF initiative_id, contribution_type
ON public.contributions
FOR EACH ROW
EXECUTE FUNCTION public.validate_monthly_payment_domain();

CREATE TRIGGER trg_validate_monthly_allocation_domain
BEFORE INSERT OR UPDATE
ON public.contribution_allocations
FOR EACH ROW
EXECUTE FUNCTION public.validate_monthly_allocation_domain();
```

The rollback artifact also drops the two replacement triggers and then drops only the two replacement guard functions. It does not alter accounting data.

Rollback artifact:

`supabase/rollback/v1_3m_replacement_accounting_triggers_rollback.sql`

Rollback execution remains separately authorized and is **not** part of the forward migration.

#### 3. Explicit disposition of legacy allocation trigger

`trg_validate_monthly_allocation_domain` is **retired** by the forward migration.

Reason: its function rejects initiative-linked payments and therefore remains Initiative-specific legacy domain logic. The replacement allocation guard owns the canonical payment/obligation allocation invariants and contains no Initiative semantics.

The forward migration therefore explicitly drops:

```sql
DROP TRIGGER IF EXISTS trg_validate_monthly_allocation_domain
  ON public.contribution_allocations;
```

The legacy function is retained for rollback fidelity; it is not active after the forward migration.

**v1.3M.2.2 result: 🟢 PASS.**
